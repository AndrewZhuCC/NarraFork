# API 请求循环录制、固定保存与旧版 request dump

## 循环录制与 `/save_dump`

循环录制回答的是「实际发送的请求是什么、返回的流里发生了什么」。它与旧版 usage-history 的 `raw_dump_json` / `requestDumps` 溢写分开管理，不要求先把完整响应累积在内存中再保存。

- **实例级循环窗口，独立双预算。** 默认整个实例共享请求 **16 MiB**、返回 **128 MiB** 的录制预算，不是每个叙述者各自获得这些容量。容量按实际录制文件字节记账，非零窗口至少 1 KiB（需要容纳帧元数据）；请求和返回分别记账，任一侧的流量不能挤占另一侧的预算；旧内容按循环策略淘汰，单条超限和不完整内容也会明确标记，而不是声称保留了全量。循环区位于 `~/.narrafork/request-recordings/`；关闭录制、预算或错误记录配置与旧版 dump 设置分别控制，实际录制范围以提供商接入为准。
- **即时保存，不打断当前工作。** 在会话输入 `/save_dump`，或调用 `POST /api/narrators/:id/request-recordings`，将这个叙述者当前可用的录制保存到独立固定区 `~/.narrafork/saved-request-recordings/`。命令不接受参数，不调用模型、不排队，也不会因为消息带有 `interrupt` 或中断模式而停止运行中的请求。
- **截至调用时的不可变快照。** 即使上游仍在返回，保存也只截取调用时已经收到且仍在窗口内的部分；后续响应不会写进已经保存的 bundle。响应尚未结束、前段被循环淘汰或超过预算时，元数据会标记 `partial` / `truncated`，排障时必须一起查看。重新执行命令通常会产生另一份保存，不会覆盖旧证据；持续保留模式下如果当前窗口已结束并已自动固定，命令可返回最近的持续保留记录。
- **持续保留开关与手动快照不同。** 设置中的「持续保留请求 Dump」（`requestDumpEnabled`）为新请求自动创建固定记录，持续接收该请求的返回直到结束；其元数据带 `continuous`。只保留错误时，仍需先收集正在发生的返回，再在结束时决定是否固定保存错误记录；如果前段已经被循环淘汰，只能保存残存证据。`/save_dump` 只保存截至调用时的不可变部分，不会为会话开启未来追录。
- **崩溃恢复核对实际段文件。** 请求开始先持久化归属 receipt，持续模式先发布初始部分保存再接收字节。重启时有界核对 `chunks` 和 checkpoint：合法未引用段重新入账，仅截去不完整尾帧；随后按当前双预算淘汰，已固定的快照不改写。旧版未发布固定目录与 `.pending-*` 在启动/后台 checkpoint 分批回收，已发布对不被回收；只发布了 manifest 的保存会补回 summary。
- **固定区不随循环淘汰。** 固定保存也不被普通孤立文件清理顺带删除，保留到用户显式删除为止；其容量不受循环区双预算约束，磁盘占用需主动管理，核心另外设有保存数量、单份归档、磁盘压力等安全限制。存储统计分别显示 `requestRecordings`（循环区）与 `savedRequestRecordings`（固定保存区），旧版 `requestDumps` 仍独立统计。
- **下载走有界流式归档。** 不在 HTTP 主线程读取并拼装全部响应；单份 bundle 输入/ZIP 上限为 512 MiB，超限窗口在保存发布前明确拒绝。最多 2 个压缩任务、4 个包含待传输文件的下载，临时文件与 HTTP 传输有 120 秒租约，读取完成、取消、过期和进程恢复都会清理派生产物而不删除固定证据。核心接收客户端断开取消信号。ZIP 中的元数据和已有请求/响应证据应一起保留，不能把部分流当成完整响应。

### 接口与权限

沿用叙述者 ACL：保存、删除需要 **write**；列表、下载需要 **read**。不存在、无权限以及保存归属不匹配均按 **404** 隐藏，不能通过保存 ID 探测其他叙述者。保存 ID 必须符合系统 ID 格式，不能用路径或文件名替代。

| 方法与路径（前缀 `/api/narrators/:id`） | 返回 |
| --- | --- |
| `POST /request-recordings` | 直接返回 `SavedRecording`，含保存 ID、时间、请求 ID、字节数及完整性标记 |
| `GET /request-recordings?cursor=...&limit=...` | `{ items, nextCursor }`；默认 20 条，`limit` 为 1–100 的整数 |
| `GET /request-recordings/:saveId/download` | 流式 ZIP 下载 |
| `DELETE /request-recordings/:saveId` | `{ ok: true }`，仅删除这份固定保存 |

列表只返回有界元数据，不在数据库中加载大型 dump 字段，也不把宿主绝对路径作为下载指针暴露给客户端。其他客户端将 `/save_dump` 发到消息接口时，同样直接得到 `SavedRecording`，而不是创建模型消息。

### 隐私与可见性边界

请求头、URL 与可识别认证字段会做脱敏，但这不是把会话匿名化：消息正文、提示词、工具输入/输出、文件内容及上游错误中可能仍有个人信息或商业机密。录制与 ZIP 应按会话数据管理；下载和转发前检查内容，不要将其当成普通无敏感日志。固定保存长期占盘，也意味着敏感内容长期保留。

两类新录制目录属于私有平台数据：通用文件预览、下载、编辑读取和 `ShareFile` 分享不能直接读取，也不能通过区外符号链接或把祖先目录打包绕过检查。获取证据只能使用上面的叙述者 ACL 下载接口。旧版 `request-dumps` / `malformed-request-dumps` 文件预览与分享兼容性保持不变。

WebSocket 录制是 **应用层消息/帧证据**，不是网络抓包：不包含 TLS 数据包、底层网络重传或所有不可见的 SDK 行为。插件提供商仅能录制经过宿主可见接入点的请求/响应或插件显式提供的证据；插件自己发起且宿主无法观察的网络调用不能宣称已录到。

## 旧版 request dump 溢写到文件（requestDumps）

request dump 回答的是「我们到底发了什么、上游回了什么」，所以它必须完整——但完整就意味着大（含重放历史和内联图片时动辄数 MB），而主线程性能规则禁止让 SQLite 行无上限增长。两个要求只在「dump 存在数据库里」时冲突，因此按大小分流：

- **行内只留有界的头部 + 指针。** `server/lib/api-request-dump-store.ts` 的 `RAW_DUMP_INLINE_MAX_BYTES`（当前 512KiB）是**行预算**，与 `agent.requestDumpMaxSize`（运维想保留多少 dump）是两件事；早期把两者混为一谈，导致 5MB 的 dump 在 32MB 默认值下从不溢写、整块进了 `raw_dump_json`。超过行预算时行里只保留可读的 head 和 `RawDumpSpillPointer`（带 `inlineTruncated`，让前端能说明「这是头部，完整内容需下载」）。
- **完整 dump 落到 `~/.narrafork/request-dumps/`**（目录名即 `REQUEST_DUMP_SPILL_DIR`），文件名含时间戳 + requestId + 随机短 id（同毫秒两次写入不能互相覆盖，那正好毁掉别人在收集的证据）。写入有硬字节上限、失败清理和有界重试；具体数值以代码为准，不要在别处复制。
- **该目录可以安全删除，运行时不会读回。** 产品逻辑不依赖这些文件，删除只损失「下载较早 dump 的完整内容」这一项能力。溢写文件数量本身也有上限（`MAX_REQUEST_DUMP_SPILL_FILES`），旧文件按 mtime 淘汰。
- **下载路由 `GET /api/usage-history/:id/raw-dump`** 在行里有 spill 指针时直接流式返回文件（不在主线程解析再重新包装）；**文件被裁剪或手工删除时回落到行内 head 而不是 404**——用户至少拿到残存部分和解释缺失原因的指针。任何走「返回行而非文件」的分支都会先剥掉指针里的绝对路径（路径含宿主 OS 账号名，而 dump 会被转发给协助排查的人）。
- **存储扫描含 `requestDumps` 分类**（`server/services/storage-service.ts`），与 shares、worktrees、treeSnapshots 并列。
- **隐私定位：** dump 是请求的逐字副本，凭据已由 `sanitizeHeaders` 掩码，但消息正文是**故意保留**的（不看正文无法诊断被拒的请求）。按会话数据对待，不要当普通日志。
